## The loop

1. `am gen` — compile the spec, regenerate `gen/`, migrations, clients and this file.
2. `am check` — build, vet and run the Ambit analyzers; fix every finding.
3. `am test` — generated policy tests plus yours, against a real Postgres.
4. `am migrate plan` — see what the schema change costs before applying it.
5. `am diff --base main` — the behaviour change a human reviews.

## The pattern

Behaviour is declared in the module's `spec.go`; the action body only does the work.

```go
// spec.go — who may call it, what it touches, how it can fail
var SendInvoice = s.Mutation("SendInvoice",
	s.Input(s.ID("invoice_id", Invoice)),
	s.Returns(Invoice),
	s.Requires(app.Admin.Or(app.Accountant)),
	s.Writes(Invoice),
	s.Effects(s.EmailEffect()),
	s.Errors("not_draft"),
)

// actions.go — signature fixed by am gen; data via c.DB, time via c.Clock, effects via c
func sendInvoice(c *gen.SendInvoiceCtx, in gen.SendInvoiceInput) (*gen.Invoice, error) {
	inv, err := c.DB.Invoices.Get(c, in.InvoiceID)
	if err != nil {
		return nil, err
	}
	if inv.Status != gen.InvoiceStatusDraft {
		return nil, gen.ErrSendInvoiceNotDraft()
	}
	updated, err := c.DB.Invoices.Update(c, inv.ID, inv.Version, gen.InvoicePatch{
		Status: am.Set(gen.InvoiceStatusSent),
		SentAt: am.Set(c.Clock.Now()),
	}.Assignments())
	if err != nil {
		return nil, err
	}
	if _, err := c.Email.Send(c, []byte("{}")); err != nil { // sent only if the transaction commits
		return nil, err
	}
	return updated, nil
}
```

`am check` refuses `database/sql`, `net/http`, `time.Now` and `go` statements in an
action. Role checks do not belong there either: access is declared in the spec, and so
are checks against the caller. "Nobody approves their own expense" is
`s.Update(app.Approver.And(s.Not(s.Owner("submitter"))))`, not an `if` on `c.Actor.ID`.
A value rule such as a positive amount goes on the resource field (`.Min(1)`) or in
`s.Invariants`, so the database enforces it for every write, not only on one input.
`am context <module>` or `am context --action <module.Action>` prints the
spec and generated signatures for just the code you are changing.

## Rules

Access rules live in the spec, never in an action body. A query is scoped by the
tenant and the read rule before your code sees it, so a missing filter is not a leak.
`am check` fails on each of these; `am explain <ID>` shows a failing and a passing example.

## Commands

| Command | What it does |
| --- | --- |
| `am gen` | regenerate from the spec |
| `am check` | compiler, vet, analyzers, one diagnostic list |
| `am test` | generated and written tests against Postgres |
| `am migrate plan/apply/status` | schema work, classified |
| `am diff --base main` | behaviour diff for review |
| `am explain <RULE-ID>` | why a rule exists, with a fix |
| `am actor create --field email=... --role ...` | an account and API token to call the app with; run it after `am dev` starts |
